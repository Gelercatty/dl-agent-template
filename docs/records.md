# 实验记录与归档

长期操作规则放 `docs/`，假设放 `plans/`，执行证据放仓库外的 Job/Run。
只有跨实验成立的操作经验才提升为规则。

普通审查、调查、dry-run 或测试默认在对话交流，不自动写总结报告。
用户明确要求“记录”时，将结论放 `exp/YYYYMMDD/<topic>.md`，采用团队约定的日期时区。
正式训练必须有执行前计划与执行后结果，失败／中断也补全，不需再次请求记录授权。
这不额外授权训练或平台提交。

## 训练前

计划写清问题、假设、baseline、变化变量、数据版本和 split、指标、通过条件、资源预算及
失败处理。冻结后成为 `Jobs/<id>/PLAN.md`，不能事后改写原假设。

`prepare` 将计划复制到 `TRAINING_RECORD.md` 并标记尚未执行。模板仅检查计划非空，
Agent／人仍需审阅内容，不能靠字数或固定标题代替计划质量。

## 训练后

controller 自动追加来源、环境、终态、步数、指标和产物哈希。Agent／人还要补充：

- 实际配置／资源偏差，失败／中断原因和未完成的检查。
- 按原验收条件判断结果，区分测量事实、解释与下一步。
- 与本实验相关的数据泄漏、重复样本、分布变化等限制。
- 使用哪个 checkpoint，关联 Release／Job／Run ID、step 和内容哈希。

自动 success 表示执行验收通过，不等于研究假设、模型质量或产品目标通过。
teacher 生成标签应标为 pseudo-GT；不要用 test split 调参后声称是独立测试。

## 可提交结论

需要 Git 记录时，以这些内容为起点，删去不适用部分：

```markdown
# 实验问题

- 状态：planned / running / failed / complete / rejected
- 日期和时区：
- Release / Job / Run：

## 假设与通过条件

## baseline、唯一变量、数据 split 和评测协议

## 观察结果与关键数字

## 解释、限制和下一步
```

`exp/` 只放可审阅 Markdown，不放日志、配置副本、checkpoint、媒体、指标 JSON 或缓存。
公开记录使用逻辑 ID 和哈希；实际路径、平台任务 ID、主机与账号映射保存在私有 Job 记录。
提交前检查内容，避免把内部资源清单带入公开仓库。

模板通过 ID、来源哈希和终态关联 Job 定义、训练记录和 Run 产物，提供本地追溯。
对象存储上传由项目按需要接入并校验内容；模板不自动上传或删除。
保留失败证据；清理须明确 Run ID、确认任务终止并保留所需 checkpoint，不用跨项目通配符。
